# 2026-04-01 Planning Work Agent 入口模型与执行通道澄清 v1

## 1. 这份文档要冻结什么

这份文档不讨论底层代码怎么实现，先冻结第一阶段 `planning work agent` 的效果口径，回答 4 个混在一起的问题：

1. 任务、文件、会议录音、转写稿，到底从哪些入口进入系统。
2. 飞书 `OpenClawBot` 能不能作为主入口，边界是什么。
3. 第一阶段到底需不需要多 agent。
4. `public MCP`、`/v3/agent/turn`、`chatgpt_web.ask`、`gemini_web.ask` 各自是什么角色。

一句话结论：

- 第一阶段不应该承诺“飞书 = IDE / Codex TUI / Antigravity”。
- 第一阶段应该承诺“飞书可以成为高便利采集与派工入口，桌面仍保留高保真工作入口”。
- 第一阶段不要求为了形式做多 agent，但必须保留独立验收/复核能力。
- `chatgpt_web.ask / gemini_web.ask` 应收回成内部执行 lane，不再作为你脑中的产品入口。

## 2. 当前现实边界

### 2.1 Feishu / OpenClawBot 现状

当前仓里确实有 Feishu WebSocket gateway，但现实能力边界很清楚：

1. `feishu_ws_gateway` 当前把 Feishu 消息转成 `/v2/advisor/advise` 请求，默认打集成态主 API 的 `18711`，不是独立 IDE 工作面。
2. 当前 payload 明确是 `message + task_intake`，而 `attachments=[]`。
3. 当前消息解析只抽 `text` 字段。
4. 当前 gateway 显式跳过非 text message。
5. 历史 validation 文档也已经写明：`feishu_ws` 当前验证的是 text-message payload path，不是附件/富上下文场景。

这意味着：

- 现在的 Feishu 入口已经足够证明“消息型入口”是存在的。
- 但它还不能被诚实地描述为“我把录音、截图、转写、文件、微信转发内容一扔进去，系统就成熟地接住并完成分类入库”的完成态。

### 2.2 `planning` 仓当前入口现实

`planning` 仓本身已经给了一个比现在更接近你想法的入口口径：

1. `00_入口/总入口.md` 已冻结“总入口 -> 领域入口 -> 专题入口 -> 业务子目录/单一入口”的主入口纪律。
2. `00_入口/碎片收集/README.md` 已经明写这是“入口漏斗 L0”，用于收录语音转写、链接、截图说明、零星想法，目标是“不丢、可追踪、可派工”。
3. `00_入口/专题入口/外来文件专题入口.md` 也已经明写：外来文件目录不覆盖业务主入口，不应被当默认入口。

这意味着：

- 你今天如果要手工落盘，最合理的默认兜底入口不是到处猜目录。
- 默认兜底入口应该是 `planning/00_入口/碎片收集/`。
- `外来文件管理` 只能作为补充治理案例/归档区，不应该充当 planning 主入口。

### 2.3 当前 ask / agent 现实

当前代码里已经有三层现实：

1. `public MCP advisor_agent_turn` 是 northbound 高层入口，它只是把请求规范化后发到 `/v3/agent/turn`。
2. `/v3/agent/turn` 是厚入口，会根据 `goal_hint` 走 `consult`、`direct gemini lane`、`controller/chatgpt lane` 等不同执行路径。
3. `chatgpt_web.ask / gemini_web.ask` 是内部低层执行 lane，不是用户脑中的产品入口。

当前混乱感主要来自两点：

1. 入口层和执行层同时被命名成“agent”。
2. 你脑中的“我要怎么发布工作”与系统内部“最后落到哪个 provider”被混在了一起。

## 3. 第一阶段应该冻结的入口模型

### 3.1 不是单入口，而是双主入口 + 一个兜底入口

第一阶段最合理的入口模型不是“只用飞书”，也不是“只用桌面 agent”，而是：

1. `飞书 / OpenClawBot`
   - 定位：高便利采集与异步派工入口
   - 场景：手机上、会议后、微信转发后、外部文件刚收到时
   - 用户目标：先把东西可靠送进系统，不丢，不乱

2. `桌面高保真入口`
   - 形态：Codex / Claude Code / Antigravity / 桌面飞书触发后接桌面继续
   - 定位：深度交互、反复迭代、复杂审阅、长任务推进
   - 用户目标：达到接近 `Codex TUI / Antigravity IDE` 的工作效果

3. `repo 兜底入口`
   - 路径：`planning/00_入口/碎片收集/`
   - 定位：任何入口暂时接不住时的统一落盘口
   - 用户目标：不需要猜目录，也不需要担心先放错地方导致后续找不到

### 3.2 第一阶段对飞书该承诺什么，不该承诺什么

第一阶段对飞书应该承诺：

1. 你可以把消息、转发文字、截图说明、文件、录音、转写稿丢进飞书入口。
2. 系统会先给“收到回执”。
3. 系统会把输入收进统一 intake 对象，而不是散在聊天记录里。
4. 系统会做基础分类：这是项目材料、会议材料、研究线索、汇报素材、待办事项，还是纯归档碎片。
5. 系统会给出下一步去向：进入哪个项目、哪个专题、哪个工作流。
6. 对能稳定提炼的信息，系统会形成记忆候选、行动项候选、研究候选，而不是只回复一句话。

第一阶段对飞书不应该承诺：

1. 它已经等价于 `Codex TUI`。
2. 它已经等价于 `Antigravity IDE`。
3. 它已经具备成熟的多文件并排审阅、长时间来回修订、可视化 diff 与复杂工作台交互。
4. 它可以完全替代桌面高保真工作面。

更准确的口径应该是：

> 飞书第一阶段是 ubiquitous capture + task dispatch + brief review 入口，不是 full IDE workbench。

### 3.3 这对你最直接的意义

这会把你现在的纠结拆开：

1. 你不需要先想“到底丢哪个目录”。
2. 你只需要想“我要先让系统接住”，而不是“我要先自己完成分类”。
3. 真正复杂的继续加工，可以从飞书 handoff 到桌面工作面。

## 4. 第一阶段需要支持的输入类型

第一阶段要服务的是 `planning/` 高频工作，所以输入类型必须按真实工作材料来定义。

### 4.1 文本型输入

包括：

1. 你自己的任务描述
2. 微信聊天转发内容
3. 会议纪要片段
4. 零散想法
5. 外部人发来的说明文字

系统效果要求：

1. 识别这是任务、材料、事实、判断、待确认，还是仅供参考的聊天碎片。
2. 提取项目名、对象、人名、公司名、时间、结论、待办。
3. 判断是否进入某个已有项目主线，还是先放入 L0 碎片漏斗。

### 4.2 图片与截图

包括：

1. 微信截图
2. 群聊截图
3. 会议照片
4. 图表截图
5. 文档页面截图

系统效果要求：

1. 不把图片仅当附件保存。
2. 要能先生成图片内容摘要。
3. 要能把图片和对应任务/项目/会议上下文关联起来。
4. 对可结构化内容，提取成事实候选或行动项候选。

### 4.3 音频与录音

包括：

1. 会议录音
2. 面试录音
3. 客户沟通录音
4. 语音留言

系统效果要求：

1. 接住原始音频，不丢原件。
2. 明确走 `ASR -> 差异比对 -> 精校 -> 摘要/行动项/知识候选` 的生产线，而不是只给一份粗转写。
3. 输出的不是“看起来像 transcript”，而是可审计终稿、可复核差异、可回流知识候选。
4. 新开的 agent 后续应消费这些结构化产物，而不是每次重新从音频开始。

### 4.4 转写稿与文件

包括：

1. 已有转写稿
2. Excel / Word / PPT / PDF
3. 别人发来的说明文件
4. 你自己整理的 planning 材料

系统效果要求：

1. 先识别这是“正式业务材料、外部输入、过程产物、归档材料、控制资料”中的哪一类。
2. 再决定是否进入项目主线、研究主线、汇报主线或仅归档。
3. 不要求你手工决定最终路径。
4. 系统至少要能先给出“建议落点 + 建议标签 + 是否更新记忆/台账/行动项”。

## 5. 第一阶段的默认落盘与分流口径

### 5.1 今天就能冻结的人工兜底口径

如果当前某个自动入口还没接稳，默认人工兜底路径应该冻结为：

1. 未分类碎片：`planning/00_入口/碎片收集/`
2. 需要正式引用或查证的项目事实：从 `planning/00_入口/总入口.md` 进入，再走领域入口 / 专题入口
3. 纯外来参考资料：`外来文件管理`，但不能替代业务主入口

### 5.2 用户不该继续自己判断的事

第一阶段应把下面这些决定交给系统，而不是交给你：

1. 这是进 `两轮车车身业务`、`预算`、`人员与绩效` 还是 `机器人代工业务规划`
2. 这是“项目材料”还是“外来参考”
3. 这是“正式记忆候选”还是“只留原件不入库”
4. 这是否需要生成待办、行动项或研究线索

你需要决定的是意图，不是目录学。

## 6. 第一阶段到底需不需要多 agent

结论先说：

- 第一阶段不需要为了追求概念完整而强推“多 agent everywhere”。
- 第一阶段需要的是“效果上像有分工”，而不是界面上堆很多 agent 名字。

### 6.1 第一阶段的最小分工

第一阶段至少需要三类能力，但不一定要表现成三个独立前台 agent：

1. `intake / triage`
   - 接输入
   - 做分类
   - 判断去向

2. `work executor`
   - 结合历史与现状推进实际工作
   - 产出规划、诊断、纪要、汇报、任务包

3. `review / acceptance`
   - 独立挑错
   - 检查是否理解偏、漏项、口径打架、证据不够

这三类能力可以先由一个 orchestrator + 一个 reviewer lane 实现，不需要先把系统切成一堆 agent。

### 6.2 多 agent 什么时候才值得上

只有在这些场景里，多 agent 才显著有价值：

1. 高风险研究或重大决策，需要独立复核
2. 长任务需要 planner / executor / evaluator 角色分离
3. 需要双模型对照或多模型 consult
4. 需要周期性复盘、抽出共性错误并升级方法

### 6.3 第一阶段不该为了多 agent 而多 agent

如果某个任务本质上只是：

1. 接住材料
2. 分类归档
3. 生成纪要或摘要
4. 更新待办和记忆候选

那不需要为了形式把它拆成 4 个 agent。

## 7. `ChatGPT ask / Gemini ask / public MCP` 应该怎么理解

### 7.1 第一原则：把入口和执行 lane 分开

应该冻结成下面这层次：

1. `用户入口`
   - 飞书 / OpenClawBot
   - Codex / Claude Code / Antigravity
   - repo 兜底落盘入口

2. `northbound agent surface`
   - coding agent 默认是 public MCP `advisor_agent_turn`
   - Feishu WS 当前现实还是 `/v2/advisor/advise`

3. `内部执行 lane`
   - `chatgpt_web.ask`
   - `gemini_web.ask`
   - `consult`
   - 其他内部 route

### 7.2 为什么 public MCP 之后更乱

不是因为 public MCP 这个想法本身错了，而是因为三件事当时一起叠上去了：

1. 想把 ask MCP 上面再包一层 agent
2. `/v3/agent/turn` 自己又长成了厚控制面
3. 底层 provider lane 还持续暴露在很多文档与心智里

结果就是：

- 用户脑中以为自己在选入口
- 实际却在被迫理解 provider lane
- 同时又看见 public MCP、REST、ask、advisor 混在一起

### 7.3 第一阶段更合理的 lane 角色定义

第一阶段建议冻结成：

1. `ChatGPT lane`
   - 作为 planning work 的默认主 lane
   - 适合项目诊断、规划成文、汇报成文、会议纪要整合、funnel 类思考、业务写作

2. `Gemini lane`
   - 作为附件/导入/大文件/Deep Research/第二意见 lane
   - 适合大文件、多附件、Drive attach、repo import、需要 Gemini 特定能力的场景

3. `consult lane`
   - 不是默认入口
   - 只在高风险冲突判断、重大评审、明确需要双模型对照时使用

### 7.4 对用户最重要的一条口径

第一阶段不应让你天天手工决定“这次该用 ChatGPT 还是 Gemini”。

你应该描述的是工作意图和材料，系统再决定：

1. 默认走哪条 lane
2. 是否需要 second opinion
3. 是否需要进入 consult

## 8. 第一阶段应该新增的效果表述

结合你刚才的新补充，`planning work agent` 的效果目标应该再补成下面这版。

### 8.1 核心目标句

> 做一个面向 `planning/` 高频工作的长任务 agent：能从飞书或桌面入口接住任务与材料，理解意图、连接历史、判断现状、完成高质量产出，并把结果沉淀为可继续工作的记忆与任务资产。

### 8.2 需要新增写清的效果

1. 你收到一段微信转发、一组截图、一份录音或一个文件时，不需要先决定目录。
2. 你可以先把它交给系统，系统先 receipt，再 intake，再分类。
3. 系统能判断“这是信息、任务、证据、会议材料、项目更新、还是外部输入”。
4. 系统能决定“是进入某个已有项目、进入研究主题、进入汇报材料、还是先进入碎片漏斗”。
5. 对会议录音这类输入，系统应走到“可审计终稿 + 摘要 + 行动项 + 知识候选”，不是只给粗转写。
6. 对项目材料，系统应能更新项目现状、风险、下一里程碑和证据链候选。
7. 对研究和汇报材料，系统应能形成可直接继续工作的 draft，而不是一次性聊天回答。
8. 对不确定项，系统必须明确标注“待核”，不能把猜测写成既成事实。
9. 对复杂任务，系统必要时应先澄清意图，再执行，不应理解偏。
10. 对高风险输出，系统要能经过独立 review，而不是只做自评。

## 9. 对第一阶段的最终冻结口径

第一阶段建议冻结成下面这句：

> `planning work agent` 第一阶段采用“双主入口 + 一个兜底入口”模型：飞书/OpenClawBot 负责高便利采集与派工，桌面 agent 负责高保真深度工作，`planning/00_入口/碎片收集/` 负责统一兜底落盘；`chatgpt_web.ask / gemini_web.ask / consult` 退回为内部执行 lane，而不是用户脑中的产品入口；多 agent 只在独立验收、双模型复核和长任务分工确有收益时启用，不为了形式强推。

## 10. 对后续目标讨论的直接影响

基于这个冻结口径，下一轮不该再泛泛讨论“多 agent 好不好”，而应该直接落 3 件事：

1. `入口验收包`
   - 飞书入口
   - 桌面入口
   - repo 兜底入口

2. `材料 intake 验收包`
   - 文本
   - 截图
   - 音频
   - 转写
   - 文件

3. `lane policy v1`
   - 默认 lane
   - Gemini 触发条件
   - consult 触发条件
