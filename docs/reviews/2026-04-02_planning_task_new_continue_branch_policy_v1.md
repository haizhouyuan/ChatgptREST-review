# 2026-04-02 Planning Task New Continue Branch Policy v1

## 1. 目的

这份文档要冻结的是：

> 当一个新输入从飞书、Codex、Claude Code、Antigravity 或 tmuxagent 进入系统时，应该怎样判断它是 **新任务**、**继续旧任务**，还是 **从旧任务分叉的新任务**。

如果这件事不先定，后面再怎么做统一入口、checkpoint、记忆治理，都会继续乱。

## 2. 冻结 mouthpiece

对 `planning/` 第一阶段，默认决策顺序应该是：

1. 先判断这是 `continue`、`branch` 还是 `new`
2. 再决定绑定哪个 `task_id`
3. 再决定在哪个 surface 执行

而不是：

1. 先看它从哪个界面进来
2. 再把界面 session 误当成任务线程

## 3. 三个状态的正式定义

## 3.1 `continue`

`continue` 表示：

- 这轮输入仍然属于同一条 planning 工作线程
- 当前输入可以接在已有 checkpoint 后面继续推进
- 不需要新开 `task_id`

## 3.2 `branch`

`branch` 表示：

- 这轮输入与旧任务强相关
- 但目标、交付物或作用对象已经出现明显分叉
- 应新开一个 `task_id`
- 但必须保留 `parent_task_id`

## 3.3 `new`

`new` 表示：

- 这轮输入已经是新的 planning 工作
- 不应挂回任何已有任务线程
- 应创建全新的 `task_id`

## 4. 先看什么，不先看什么

## 4.1 不应作为优先判断依据

下面这些都不该直接决定 `new/continue/branch`：

1. 是从飞书进来的还是从 TUI 进来的
2. 是手机发的还是电脑发的
3. 是 Codex 还是 Claude Code 在执行
4. 这轮材料比上一轮多还是少

这些只能说明 **surface 变化**，不能说明 **任务线程变化**。

## 4.2 应优先看的 5 个判断点

应按下面顺序判断：

1. **当前目标是否还是同一件事**
2. **当前作用对象是否还是同一项目 / 主题 / 专题**
3. **当前主交付物是否还是同一类**
4. **已有 checkpoint 是否仍然可承接**
5. **这轮只是补材料 / 迭代 / 改稿，还是已经变成另一项工作**

## 5. `continue` 的判定规则

满足下面大多数条件时，应默认判定为 `continue`：

1. 目标还是同一件事
2. 作用对象还是同一项目或主题
3. 主交付物没有变
4. 这轮输入只是补材料、继续分析、继续改稿、继续推进
5. 现有 checkpoint 的 `current_objective` 和 `next_actions` 仍可承接

### 典型例子

1. “把昨天的北美镁合金项目诊断稿再改成董事长版”
2. “我又补了一份会议转写，继续整理行动项”
3. “在原研究结论稿里补一节竞争对手情况”
4. “继续推进上次的人力规划，补岗位优先级”

### `continue` 的默认动作

1. 绑定已有 `task_id`
2. 读取最新 checkpoint
3. 把本轮输入合并到该任务的 L1 working memory
4. 更新 `checkpoint.next_actions`

## 6. `branch` 的判定规则

满足下面任一高权重条件时，应优先判定为 `branch`：

1. 仍是同一项目 / 主题，但主交付物已经明显变化
2. 仍是同一批背景材料，但作用对象已经变化
3. 原任务只是研究/纪要，这轮变成正式方案或正式汇报
4. 原任务继续推进会让旧 checkpoint 变得非常混乱

### 典型例子

1. 从“会议纪要与行动项”分叉出“年度组织规划方案”
2. 从“研究结论稿”分叉出“对董事长的决策摘要”
3. 从“内部项目诊断稿”分叉出“客户沟通稿”
4. 从“一个总研究任务”分叉出“两个独立专题深挖任务”

### `branch` 的默认动作

1. 新建 `task_id`
2. 写入 `parent_task_id`
3. 复制必要背景，但不复制全部 L1 工作记忆
4. 生成新的初始 checkpoint
5. 在新 checkpoint 里记录 `branch_reason`

## 7. `new` 的判定规则

满足下面任一高权重条件时，应优先判定为 `new`：

1. 目标已经完全不同
2. 作用对象已经完全不同
3. 主交付物和旧任务没有连续关系
4. 原任务已完成，这轮是新的 planning 工作
5. 没有任何现有 checkpoint 能合理承接

### 典型例子

1. 从“某项目阶段诊断”跳到“年度预算汇总”
2. 从“某次会议纪要”跳到“招聘编制方案”
3. 从“某技术研究”跳到“客户报价稿”

### `new` 的默认动作

1. 创建全新 `task_id`
2. 不继承旧任务 L1 working memory
3. 只在必要时引用旧任务的 L2 项目/主题记忆

## 8. 决策流程 v1

## 8.1 一次标准判断

每次新的输入进入时，按下面 6 步判断：

1. 识别当前输入所指向的项目 / 主题 / 专题
2. 找最近候选 `task_id`
3. 读取该候选任务的最新 checkpoint
4. 比较：
   - `current_objective`
   - `current_output_target`
   - `project_or_topic_ref`
   - `current_status`
5. 决定：
   - `continue`
   - `branch`
   - `new`
6. 把这个决策写成结构化记录

## 8.2 最小决策记录

每次判断至少应落一条对象：

```json
{
  "decision_type": "continue",
  "task_id": "task_xxx",
  "parent_task_id": null,
  "reason": "same project, same deliverable, checkpoint still usable",
  "confidence": "high",
  "evidence": [
    "project_or_topic_ref matched",
    "output target still the same"
  ],
  "clarify_needed": false
}
```

## 9. 需要澄清的情况

下面这些情况不应直接硬判，而应先澄清：

1. 目标描述很短，无法判断交付物
2. 同一主题下最近存在多个候选任务
3. 用户同时发来多类输入，可能包含多个任务
4. 原任务看起来已完成，但这轮像是返工或追问

### 澄清问题模板

第一阶段建议只问最少的 3 类问题：

1. “这是继续上次那件事，还是新开一件事？”
2. “这轮主要是继续产出同一个文档，还是要转成另一类交付物？”
3. “这轮主要服务哪个项目 / 主题 / 对象？”

## 10. 三类高频场景的默认判法

## 10.1 会议材料类

### 默认 `continue`

适用于：

- 同一场会的补录音、补转写、补截图、补微信转发

### 默认 `branch`

适用于：

- 从会议纪要分叉出正式方案、正式汇报、正式决策稿

## 10.2 研究类

### 默认 `continue`

适用于：

- 同一研究主题继续补证据、补图表、补判断

### 默认 `branch`

适用于：

- 从研究稿分叉出领导摘要、客户版、专项深挖子题

## 10.3 项目管理类

### 默认 `continue`

适用于：

- 同一项目的阶段诊断、风险更新、里程碑推进

### 默认 `branch`

适用于：

- 从项目现状诊断分叉出预算方案、对外沟通稿、专项复盘

## 11. 第一阶段最该避免的误判

1. 因为换了入口就误开新任务
2. 因为是同一项目就把所有工作都塞进一个旧任务
3. 因为材料相关就误判成继续任务，忽略了交付物已改变
4. 因为怕麻烦就不做 `branch`，导致单个任务线程越来越脏
5. 因为没找到旧窗口就误以为只能新开任务

## 12. 一句话结论

`planning/` 第一阶段对任务线程的默认规则应该是：

> 同一目标、同一对象、同一主交付物，就默认 `continue`；同源但交付物或作用对象明显分叉，就 `branch`；目标和对象都已经换了，才 `new`。
