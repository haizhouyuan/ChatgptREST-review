# Planning 工作助手规划说明（非技术版）v1

## 一、这件事我们到底在做什么

简单说，我们现在不是在做一个“聊天机器人”，也不是在做一个“技术玩具”。

我们真正想做的是：

**做一个能帮你长期处理 `planning/` 目录里日常工作的工作助手。**

这个助手未来要能做的事情，核心包括：

1. 接住你平时发来的任务、材料、会议录音、转写、截图、微信转发内容。
2. 看懂这些材料是什么，属于哪个项目、哪个主题、哪类工作。
3. 结合 `planning/` 里已经有的历史文档、项目台账、研究结论、汇报稿，继续往下做。
4. 不是只给你泛泛建议，而是产出能直接用的东西。
5. 做完以后还能记住重要结论，下次继续，不用每次都从零开始。

换句话说，我们要做的是一个：

**面向你真实工作、能长期接任务、能持续推进、能留下记忆的 planning 工作助手。**

## 二、为什么之前会越做越乱

这个问题，其实不是因为你目标错了，而是因为过去好几个目标一起推进，没有先分清主次。

最早你想解决的是：

1. 更方便发任务
2. 更强的 agent 能力
3. 更好的多模型协作
4. 更好的长期记忆
5. 更像 Anthropic harness 那种长任务工作方式

这些目标本身都合理。

但问题在于，当时没有先定清楚：

1. 第一阶段最重要的目标是什么
2. 哪些东西只是辅助能力
3. 哪些入口是真入口，哪些只是内部封装
4. 会话、任务、记忆这三件事到底怎么区分

结果就是：

1. 入口越来越多
2. 工具越来越多
3. 名词越来越多
4. 但“真正怎么用、怎么持续做完一件工作”反而越来越不清楚

所以这次我们做的第一件大事，不是继续加功能，而是**先复盘、先收口、先把主线定出来**。

## 三、我们这次是怎么一步步收口到现在的

这轮其实不是一下子得出结论的，而是一步一步往下收的。

### 第一步：先确认现状到底是什么

我们先做的，不是谈理想目标，而是认真核对现状：

1. 代码现在到底在做什么
2. 文档里有哪些冲突
3. 哪些是已经真的在用的
4. 哪些只是开发过但没形成稳定使用法

这一步得出的结论是：

**你现在真正高频在用的主工作台，不是飞书，也不是 ChatgptREST 的某个 ask 接口，而是 `Codex / Claude Code / Antigravity`。**

同时，你手机上通过 `tmuxagent(8702)` 去操作这些 pane，本质上也还是在用这套主工作台。

### 第二步：把“入口”和“执行层”分开

之前很容易混在一起的一个问题是：

“我从哪里发任务”和“任务到底靠什么能力执行”不是一回事。

我们这次把它拆开了：

1. 你真正干活的地方，是 `Codex / Claude Code / Antigravity`
2. `tmuxagent(8702)` 是远程继续这些工作台的入口
3. `Feishu / OpenClawBot` 更适合做收件箱、派工和轻交互
4. `chatgpt_web.ask / gemini_web.ask` 这些更像内部专项能力，不是日常主工作台

这一步很重要，因为它纠正了以前“什么都像入口、什么都像主线”的混乱。

### 第三步：把第一阶段真正目标定下来

这一步我们明确了：

第一阶段不是去追求“什么都做”，而是先把一件事做好：

**先做一个面向 `planning/` 日常工作的长任务 agent。**

它要优先服务你的高频工作：

1. 人员规划
2. 项目规划
3. 项目现状诊断
4. 研究到决策稿
5. 会议沉淀
6. 汇报材料

也就是说，这一阶段我们先对准你的真实工作，而不是继续扩散到很多看起来很强、但实际不一定最先解决问题的方向。

### 第四步：把“高质量”翻成可验收的话

以前“高质量”容易说得很抽象。

这次我们把它收成了 5 条：

1. 不理解偏
2. 不漏项
3. 口径一致
4. 可直接使用
5. 可核验

这一步的意义是：

后面不是只看“模型回答得像不像”，而是看它能不能真的达到你工作的标准。

### 第五步：接受多端并存，但不接受多头记忆

这一点是这轮最关键的转折之一。

我们没有再坚持“必须只有一个入口”，因为这不现实，也不符合你的使用习惯。

现在已经接受的现实是：

1. 你会继续用 `Codex / Claude Code / Antigravity`
2. 你也希望飞书能成为方便入口
3. 你有时还会用手机通过 `tmuxagent` 继续任务

所以问题不该再是：

- “到底只选飞书还是只选 TUI”

而应该变成：

- “多端都可以，但同一件工作必须有同一个任务线程和记忆体系”

### 第六步：把真正该统一的东西定出来

这一步，我们最终定下来：

未来真正要统一的，不是界面，而是这四件事：

1. `task_id`
2. `checkpoint`
3. `memory scope`
4. `新任务 / 继续旧任务 / 分叉任务` 规则

这四样东西，就是后面多端协作、长期推进、不再混乱的基础。

## 四、现在已经定下来的核心方案，用大白话怎么说

### 1. 先不追求“只有一个入口”

我们现在接受：

1. 飞书可以是入口
2. Codex/Claude Code/Antigravity 还是主工作台
3. 手机上的 `tmuxagent` 是远程继续工作台的方法

但以后不应该再因为“换了个入口”就等于“换了一件任务”。

### 2. 一件工作要有一个稳定任务编号

以后最理想的状态是：

不管你是从飞书发、从电脑里的 Codex 发、还是从手机上的 tmuxagent 继续，

只要本质上还是同一件工作，它就应该挂在同一个 `task_id` 下面。

这就像你给一件工作配了一个“工作线程号”。

界面可以换，线程不能乱。

### 3. 每个任务都要有一个“接力棒”

这个“接力棒”就是 `checkpoint`。

它的作用很简单：

当你下次回来，或者换了一个入口、换了一个终端时，不用翻所有旧聊天，而是直接看这个 checkpoint 就知道：

1. 现在做到哪了
2. 已经确认了什么
3. 还缺什么
4. 下一步应该做什么

这相当于给每件工作配一个随时可交接的“任务卡片”。

### 4. 记忆要分层，不能什么都乱记

之前一个很容易出问题的地方是：

什么都想记，结果最后真相和草稿混在一起。

所以现在我们把记忆分成了几层：

1. **当前会话里的临时想法**
   - 可以随时丢掉
2. **这个任务当前阶段需要记住的内容**
   - 为了下次继续做
3. **项目或主题的长期稳定事实**
   - 真正值得沉淀下来的
4. **做事方法上的经验教训**
   - 用于以后改进系统

这样以后就不会再把：

1. 一时猜测
2. 中间草稿
3. 正式结论
4. 方法经验

全都混成一锅。

### 5. 以后每个新输入，都先判断它属于哪种情况

现在已经定下来的规则是：

#### `继续旧任务`

如果目标没变、对象没变、主要交付物也没变，那就继续旧任务。

例如：

1. 继续改昨天那份项目诊断稿
2. 给同一个会议纪要补一份新转写
3. 在原研究稿上补充一段新内容

#### `从旧任务分叉`

如果还是同一件大背景，但交付物变了、用途变了，那就从旧任务分叉出一个新任务。

例如：

1. 会议纪要分叉出正式方案
2. 研究稿分叉出给董事长看的摘要
3. 内部工作稿分叉出对外客户稿

#### `新任务`

如果目标、对象、交付物都换了，那就是新任务。

例如：

1. 从项目诊断切到年度预算
2. 从会议纪要切到招聘编制

这一步的意义非常大，因为它能避免两个极端：

1. 什么都往一个旧任务里塞，越塞越乱
2. 什么都新开，最后线程碎成一地

## 五、为什么我们没有一上来就强推飞书做唯一主入口

因为现在现实是：

1. 你在 `Codex / Claude Code / Antigravity` 上的真实工作效果更好
2. 飞书目前更像一个方便的收件箱和派工入口
3. 如果现在硬把飞书承诺成“唯一主工作台”，大概率会让效果倒退

所以我们现在更稳的走法是：

1. **飞书先做统一入口**
   - 扔材料
   - 发任务
   - 看状态
   - 继续旧任务
2. **深度工作还是交给主工作台**
   - Codex
   - Claude Code
   - Antigravity
3. **以后如果飞书体验真的做到了，再逐步升级**

这比一开始就喊“全部统一到飞书”更稳。

## 六、Anthropic harness 那套东西，现在放在什么位置

你之前提到的 Anthropic harness，其实并没有被否定。

只是现在它的位置更清楚了：

它不是第一步先做的“最终形态”，而是第二阶段用来保证质量和长任务稳定性的机制。

简单说：

1. 第一阶段先把任务线程、checkpoint、记忆分层这些基础秩序立起来
2. 第二阶段再把 planner、generator、evaluator、独立验收、chunk contract 这些东西接上

这样顺序更稳。

否则如果基础任务层都没定清楚，harness 只会叠加复杂度。

## 七、我们现在已经走到哪一步了

可以把现在的进展理解成：

### 已经完成的部分

1. 现状已经复盘清楚
2. 第一阶段目标已经定清楚
3. `planning/` 的主要工作类型已经梳清
4. 验收标准已经初步定义
5. 入口和工具分工已经基本理顺
6. 统一逻辑任务层已经定下来
7. 三个关键规则已经定下来：
   - 新任务 / 继续任务 / 分叉任务
   - checkpoint
   - 记忆写回

### 还没开始真正产品化落地的部分

1. 飞书入口怎么实际判断新任务和继续任务
2. checkpoint 具体以什么形式写、写到哪里、怎么更新
3. 记忆写回怎么真正接进系统
4. 多端怎么真正共享同一个任务线程

所以我们现在的状态可以理解成：

**第一阶段的“做法”已经理清了，但还没正式开始把它做成产品流程。**

## 八、下一步最合理的做法是什么

从你的角度看，接下来最值得做的，不是再继续发散，而是按顺序往下落地。

我建议后面按这条线推进：

### 第一步

先把“任务线程”这套东西做成能实际运行的最小闭环。

也就是：

1. 新任务怎么开
2. 继续旧任务怎么接
3. checkpoint 怎么保存和更新

### 第二步

让飞书先具备“统一入口”的最小能力。

不是一开始就替代主工作台，而是先做到：

1. 发任务
2. 继续旧任务
3. 扔材料
4. 看状态

### 第三步

再把深度工作台和飞书连到同一个任务线程上。

这样你以后无论从飞书回来，还是从 Codex/Claude Code/Antigravity 继续，都是接着同一个任务做。

### 第四步

在这个基础上，再接 Anthropic harness 那套更强的质量控制机制。

### 第五步

最后再做 EvoMap 那种持续复盘和能力进化。

## 九、如果用一句最通俗的话总结现在的方案

一句话就是：

**我们现在不是先去做一个“无所不能的大系统”，而是先把你的 planning 日常工作，变成一条能跨飞书、Codex、Claude Code、Antigravity 和 tmuxagent 持续推进、不乱、不丢、不重复开工的任务线程。**

等这条主线稳定了，再往上叠更强的 agent 能力、harness 机制和复盘进化能力。

## 十、你现在最需要记住的 5 句话

1. 这次的目标不是做聊天机器人，而是做 planning 工作助手。
2. 现在先不强求只有一个界面，而是先统一任务线程。
3. 一件工作以后要靠 `task_id + checkpoint` 持续推进，而不是靠翻旧窗口。
4. 飞书先做入口和收件箱，深度工作先继续用你现在最顺手的主工作台。
5. 先把这条主线跑顺，再接更复杂的 harness 和 EvoMap。
